# Using your own domain

In my example, I have registered the domain **`ekcloud.dk`**. To use your own domain, replace `ekcloud.dk` everywhere it appears in the committed files:

**[tls/nginx.conf](../tls/nginx.conf)** — four occurrences:

- line 6: `server_name ekcloud.dk www.ekcloud.dk;` (HTTP redirect block)
- line 12: `server_name ekcloud.dk www.ekcloud.dk;` (HTTPS block)
- line 14: `ssl_certificate /etc/letsencrypt/live/ekcloud.dk/fullchain.pem;`
- line 15: `ssl_certificate_key /etc/letsencrypt/live/ekcloud.dk/privkey.pem;`

**[tls/compose.yaml](../tls/compose.yaml)** — two occurrences:

- `/etc/letsencrypt/live/ekcloud.dk:/etc/letsencrypt/live/ekcloud.dk:ro`
- `/etc/letsencrypt/archive/ekcloud.dk:/etc/letsencrypt/archive/ekcloud.dk:ro`

You also need to substitute your domain into the `certbot` command in the manual setup section below.

If you'd rather do all the file substitutions in one shot, run this from the repo root:

```bash
$ sed -i '' 's/ekcloud\.dk/<yourdomain.com>/g' tls/nginx.conf tls/compose.yaml
```

(Drop the `''` after `-i` if you're on Linux instead of macOS.)

# Prerequisites

## Prerequisite: Docker on the server

If your server is fresh and doesn't have Docker yet, see the install commands in [infrastructure/inline_commands.sh](../infrastructure/inline_commands.sh).

---

## Prerequisite: Confirm your domain

You should also have confirmed the A records are pointing to your server:

```bash
$ dig A <yourdomain.com> +short
$ dig A www.<yourdomain.com> +short
```

---

## Prerequisite: GitHub Action secrets

The workflow at [.github/workflows/continuous_delivery_deployment.yaml](../.github/workflows/continuous_delivery_deployment.yaml) needs these repo secrets (set them with `setup.sh` or `gh secret set`):

- `CR_PAT` — GitHub PAT with `write:packages` (for ghcr.io)
- `DOCKER_GITHUB_USERNAME` — your GitHub username
- `SSH_HOST` — the public IP of your server
- `SSH_USER` — the user the workflow connects as
- `SSH_PRIVATE_KEY` — the private key matching the public key in that user's `~/.ssh/authorized_keys`

# One-time setup on the server: free port 80 and get the certificate

If you previously deployed the `continuous_deployment` stack on this server, an old nginx is bound to port `80`. Stop it (and anything else holding the port) so `certbot --standalone` can bind for the HTTP-01 challenge.

SSH in, then:

```bash
$ sudo docker ps
$ sudo docker stop $(sudo docker ps -q --filter "publish=80")
$ sudo dnf install -y epel-release
$ sudo dnf install -y certbot
$ sudo certbot certonly --standalone -d <yourdomain.dk> -d www.<yourdomain.dk>
$ sudo ls /etc/letsencrypt/live/<yourdomain.dk>/   # fullchain.pem + privkey.pem
```

On AlmaLinux 9, `certbot` lives in the EPEL repository, which is why the `epel-release` install comes first.

Drop the second `-d` flag if you skipped the `www` A record in the previous tutorial.

Certbot will ask for an email (for renewal warnings) and agreement to the Terms of Service. On success, your cert lands in `/etc/letsencrypt/live/<yourdomain.com>/` — exactly where [tls/compose.yaml](../tls/compose.yaml) expects to mount it into the nginx container.

You only need to do this **once**. Subsequent deploys reuse the existing cert.

# Trigger the deployment workflow

Push to the `tls` branch (or use the **Run workflow** button on the Actions tab for `workflow_dispatch`). The workflow:

1. Builds two images and pushes them to GHCR:
   - `ghcr.io/who-knows-inc/whoknows_variations_server-tls:latest` (Flask)
   - `ghcr.io/who-knows-inc/whoknows_variations_nginx-tls:latest` (nginx with `nginx.conf` baked in)
2. Copies `tls/compose.yaml` and a generated `.env` to `~/tls/` on the server.
3. SSHes in and runs `docker compose pull && docker compose up -d`.

The image names intentionally end in `-tls` so they don't collide with the `continuous_deployment` branch's images on GHCR.

# Verify that it worked

In a browser, hit `https://<yourdomain.com>`. Port `80` should automatically redirect to `443`. Same for `www.<yourdomain.com>`.

From your local machine:

```bash
$ curl -I https://<yourdomain.com>
$ curl -I http://<yourdomain.com>          # expect 301 to https
```

# Files involved

- [tls/Dockerfile](../tls/Dockerfile) — builds the nginx image with `nginx.conf` copied in
- [tls/nginx.conf](../tls/nginx.conf) — terminates TLS on `443`, redirects `80 → 443`, reverse-proxies to `whoknows_flask:8080` over the internal Docker network
- [tls/compose.yaml](../tls/compose.yaml) — orchestrates Flask + nginx-with-TLS, mounts the Let's Encrypt cert as a read-only host volume

# Certificate renewal

Let's Encrypt certificates expire after 90 days. Test renewal with:

```bash
$ sudo certbot renew --dry-run
```

Because the TLS nginx is bound to port `80`, the next real renewal needs that port free again — either stop the nginx container during renewal, or switch to the `--webroot` plugin (out of scope for this tutorial) so renewals can happen without downtime.
